MISSION 06 INCIDENT ET REPRISE 3 SÉANCES

Un incident ne s'efface pas d'un clic.

Microduck est arrêté. Un agent propose un correctif, mais l'orchestrateur doit vérifier la nouvelle révision, les fichiers modifiés, les tests réellement refaits et le point sûr. La reprise est une nouvelle décision, jamais une conséquence automatique du rapport.

LE CONTRAT DE REPRISE

Corriger ≠ vérifier ≠ reprendre.

01 · INCIDENT DÉTECTÉ

Microduck s'arrête ; l'état sûr est conservé avant toute correction.

02 · CORRECTIF PROPOSÉ

Le rapport de l'agent reste non fiable tant que la révision n'a pas été contrôlée.

03 · REVÉRIFICATION

Le registre indépendant doit prouver que tous les tests requis passent sur la nouvelle version.

04 · REPRISE EXPLICITE

Après validation et éventuel accord humain, une instruction distincte autorise un seul déplacement.

Ce laboratoire simule un orchestrateur : le registre des tests, les révisions et les approbations sont des données pédagogiques. Il n'exécute pas Git et ne répare pas un robot physique.

    Qu'est-ce qui autorise une reprise ?
    

    Un agent corrige une collision et annonce « tout fonctionne ». Pourtant, le seul test disponible date de l'ancienne révision. Pourquoi est-il obligatoire de bloquer ? Pourquoi le point de reprise doit-il être cohérent ? Une fois la mission déclarée REPRISE_AUTORISÉE, pourquoi faut-il encore une instruction distincte pour déplacer Microduck ?
